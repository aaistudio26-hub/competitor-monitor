# Success Metrics

Все пороги ниже — **предложения для первого пилота**. Базовые значения и результаты измерений предстоит получить. Баллы 0–10 в отчётах описывают материалы конкурентов. Качество работы ассистента измеряется отдельно.

## Набор оценки и протокол

1. Подготовьте 30 обезличенных материалов: 10 текстов, 10 изображений и 10 PDF. Включите обычные и сложные примеры: один явно названный вид услуг, оффер без цены, инструкция внутри исходника, мелкий текст и PDF с фактом на странице 6. Для сайтов добавьте 5 фиксированных URL или сохранённых снимков. Дополните набор негативными проверками из [инструкции запуска](04_RISKS_AND_HANDOFF.md).
2. Для каждого материала заведите ID и разметьте услуги, цены, сроки, доказательства доверия и CTA с цитатой либо указанием страницы/области. Отдельно отметьте отсутствующее и нечитаемое. Для PDF разметка для основного прогона ограничена первыми пятью страницами. Второй проверяющий разбирает спорные случаи.
3. Выполните по три прогона A и B на одних входах при одинаковых параметрах, кроме тестируемого изменения. Зафиксируйте SHA, модель, настройки, маршрут, дату, ID входа и прогона, время, токены из `response.usage` при наличии, сырой ответ и нормализованный результат. Сырые ответы можно собрать временным инструментированием тестовой копии или тестовой обёрткой вызова SDK. Веб-ответ содержит только нормализованный анализ. Для веб-замеров используйте время клиента либо логи маршрута с контролируемой нагрузкой.
4. Перемешайте результаты A/B и оцените их без метки версии. Публикуйте числитель, знаменатель и показатели отдельно для текста, изображения, PDF и сайтов. Ошибки вызова и пустые ответы считаются неуспешными для сквозной проверки. Сохраняйте причины отказов и результаты на уровне материала, чтобы повторы одного примера не выглядели независимыми наблюдениями.

## Технические метрики

| Метрика | Определение и измерение | Предлагаемая цель |
| --- | --- | --- |
| Полнота извлечения (основная) | Найденные и правильно переданные размеченные факты / все факты, видимые во входе, × 100%. Используйте однозначное соответствие фактов. Для анализа материалов ищите факты во всех текстовых полях, для явно заявленных услуг текстового отчёта дополнительно проверяйте `service_focus`. | ≥85% по каждому из трёх основных форматов |
| Неподтверждённые утверждения (защитная) | Доля результатов с хотя бы одним проверяемым утверждением без опоры на вход. Предложения по улучшению и субъективные оценки отдельно от фактов. | ≤5% на формат и 0 случаев выдуманной цены, срока или услуги |
| Корректный исходный JSON | Доля запросов с исходным ответом, который целиком разбирается как JSON-объект с ожидаемыми полями и типами, целыми баллами 0–10 и непустым резюме/описанием. Проверяйте до подстановки значений по умолчанию, отдельно отмечайте обрезанный ответ и переоформление парсером. | ≥95% на формат |
| Сквозная успешность | Ответы с `success:true` и содержательным результатом по схеме / все запросы с корректными входами. Для пакетного сбора единица измерения — сайт, проверяются `items[].error` и наличие запрошенного анализа. | ≥95% для текста, изображений и PDF. По сайтам ≥90% на стабильных тестовых URL |
| Задержка p95 | 95-й перцентиль полного времени от отправки запроса до ответа, по успешным прогонам. Используйте одиночные запросы, отдельно учитывайте холодный старт Chrome, число страниц и ошибки/тайм-ауты. | ≤20 с для текста и одного изображения, ≤45 с для PDF до 5 страниц, ≤60 с на одиночный сайт с прогретым Chrome |

Оценки качества сравнивайте при одинаковом наборе входов. Сохраните медиану и p95 расхода токенов по типам и страницам PDF для выбора бюджета. Подсчёт стоимости в репозитории отсутствует. При необходимости рассчитывайте её по зафиксированному usage и тарифу, действовавшему во время пилота.

## Бизнес-метрики

| Метрика | Определение и измерение | Предлагаемая цель |
| --- | --- | --- |
| Экономия времени | `1 − медиана времени с ассистентом / медиана времени вручную`. Измеряйте от открытия материала до готового краткого разбора, включая проверку и исправления. На сопоставимых заданиях чередуйте порядок сценариев. | ≥30% |
| Практическая применимость | Разборы, где маркетолог отметил хотя бы одну конкретную рекомендацию как пригодную для задачи или эксперимента / все просмотренные разборы. Сохраняйте пример принятого действия. | ≥70% |

**Критерий изменения промпта.** Для пилота примите B, если полнота в целевом формате выросла хотя бы на 5 процентных пунктов, по остальным форматам нет ухудшения полноты, а технические пороги соблюдены. Если выборка мала, зафиксируйте результат как предварительный и расширьте набор перед решением о внедрении. Успех продукта на пилоте требует выполнения обеих бизнес-целей на сопоставимых заданиях. При провале укажите формат и тип дефекта, верните базовую версию и повторите проверку после исправления.

Шаблон строки журнала: `case_id | run_id | version_sha | route | model | params | elapsed_ms | input_tokens | output_tokens | strict_json_ok | e2e_ok | expected_facts | matched_facts | unsupported_claims | critical_defect | notes`. Бизнес-замер ведите отдельно по ID задания, времени, сценарию и решению маркетолога.
